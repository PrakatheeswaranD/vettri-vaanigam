# Jury Q&A

Concise, defensible answers to the questions this architecture invites.
Each answer maps to something actually verifiable in the repository, not
a rehearsed line — file references are given so any answer can be proven
on the spot.

## "Why only two agents?"

We deliberately use exactly two meaningful AI agents — the Buyer Agent
and the Merchant Agent. Policy, risk, authorization, payment state, and
financial truth remain deterministic application code (`packages/domain`,
`apps/api/src/modules/policy`, `.../commerce`, `.../payments`). Verified:
no `RiskAgent`/`PolicyAgent`/`RecoveryAgent`/`PaymentAgent` exists
anywhere in the codebase.

## "Why not a multi-agent swarm?"

More agents would add orchestration complexity without improving
financial safety or the core demonstration. A Recovery Agent, for
example, would still have to hand off to the exact same policy/approval/
authorization pipeline the Merchant Agent already uses — so building one
would only add an extra hop, not extra safety.

## "How do you stop hallucinated products?"

The model can only ever reference product IDs from a bounded candidate
set the application supplies it (search results, configured
relationships). A recommendation or proposal referencing any other ID is
rejected by a deterministic grounding validator
(`recommendation-grounding.ts`, `growth-proposal-validation.ts`) and
falls back to a labeled deterministic answer — proven directly by a
scripted fixture provider proposing an invented product ID in
`merchant-agent.test.ts` and `recovery.test.ts`, both caught and rejected.

## "How do you stop a 100% discount?"

The model cannot authorize a discount at all. `MerchantGrowthConfig`
bounds what the Merchant Agent may even *propose* (10%/15% ceilings);
`MerchantPolicy` (a separate, independently configured hard limit —
8% in this demo, deliberately lower than the proposal ceiling) is what
the deterministic Policy Engine actually enforces. A proposal that clears
the first ceiling can still be legitimately `DENY`ed by the second —
verified live in this session's own walkthrough: a Merchant Agent
recovery proposal requesting a 10% discount was denied by policy with
"requested discount 10% exceeds the maximum permitted discount of 8%."

## "How do you know a payment actually succeeded?"

Payment truth comes only from a signature-verified Razorpay webhook or a
direct authenticated fetch from the provider — never from the LLM, never
from the frontend. The browser's own Checkout callback is treated as the
lowest-confidence evidence tier: even a cryptographically valid signature
only earns the right to call Razorpay directly and trust *that* response.

## "What happens if the webhook arrives twice?"

It is processed idempotently against a deterministic event fingerprint.
Verified: delivering the same `payment.captured` event twice produces
exactly one `PAYMENT_CAPTURED` ledger event and one order-paid transition
— on both a first attempt and a recovered second attempt.

## "What if events arrive out of order?"

The deterministic payment state machine (`payment-state.ts`) rejects any
transition that would regress a terminal state. A late `authorized` event
arriving after `captured` is accepted as a validly signed event but
rejected as a *transition* — recorded as
`PAYMENT_STATE_TRANSITION_REJECTED` — and the payment stays `CAPTURED`.

## "What about a payment timeout?"

Timeout is treated as uncertainty (`UNKNOWN`), never as failure. An
`UNKNOWN` payment must be reconciled against the provider before any
recovery attempt is even evaluated — verified: seeding a payment as
`UNKNOWN` and requesting recovery triggers a real reconciliation call
first, and eligibility is derived from the state *after* reconciliation.

## "Why does Agentic Readiness matter?"

AI buyers can only transact reliably with merchants they can understand
structurally — price, inventory, variant, and policy data that a
language model can ground its answers in. The score measures exactly
that prerequisite and names the specific evidence gap behind every point
lost (e.g. "18% of products are missing return-policy information"),
never a vague number.

## "Why isn't the readiness score generated by AI?"

Because it's an operational metric that must be reproducible and
explainable on demand — recomputing it twice with no data change produces
the identical score (verified by test), which an LLM-generated score
could not guarantee. `apps/api/src/modules/readiness/engine.ts` has zero
AI-provider dependency.

## "What's actually unique here, versus a generic recommendation demo?"

Readiness is wired to actionability, not just displayed: this
repository's own seed data has a real product with deliberately
unrecorded inventory, and every growth proposal touching it surfaces a
`blockedOpportunities` entry naming the exact blocker
(`UNKNOWN_INVENTORY`) and the exact readiness dimension it depresses —
verified live in this session (Growth page, "Cross-sell blocked:
Inventory has never been recorded for this product").

## "Do you support ACP/AP2/UCP/x402?"

No, and we don't claim to. We built one clean internal
`CommerceGateway`/`PaymentGateway` boundary that is protocol-shaped —
narrow, named methods, no generic execute-anything surface — so a future
protocol adapter could sit behind it without changing calling code. We
did not implement or certify any external protocol, and the README says
so explicitly.

## "Is this production-ready?"

The demonstrated checkout → payment → recovery path is hardened per
`docs/SECURITY.md`: server-side amount authority, deterministic
authorization, signature verification, idempotency, bounded recovery,
auditability. Peripheral prototype surfaces intentionally use lighter
rigor. There is no production multi-tenant identity system, no KYC/AML,
no production-grade rate limiting, and no live Razorpay Test Mode
transaction was completed in this environment (no credentials
configured) — all stated plainly in `PROGRESS.md`'s Known Issues rather
than glossed over.

## "Is Trust Trace just a nicer-looking log viewer?"

No — it's a typed transformation (`apps/web/src/features/trust-trace/
model.ts`, unit-tested) over the real ledger trace endpoint, not a raw
dump. It groups events into the canonical governance stages, derives
each stage's status from the actual event data (never hardcoded), and
labels every actor AI/Deterministic/Human/Provider so the exact point
AI authority stops is visually obvious. A recovered payment correctly
renders as separate "Payment Attempt 1 (Failed) → Recovery → Payment
Attempt 2 (Captured)" stages, not one confusing merged block.

## "Break the Agent looks scripted — is it really live?"

Every attack calls a real production function: `validateGrowthProposal`,
`issueExecutionAuthorization`, `evaluateRecoveryEligibility`, and
`getAgentCatalogProduct` are the exact same functions the golden path
uses — verified by `apps/api/src/sandbox.test.ts` driving the real HTTP
route. Nothing about the "blocked" result is templated in the frontend;
the backend computes it fresh on every click.

## "What didn't you finish, and why?"

A second recovery attempt after the first also fails is bounded by
policy but has no UI beyond "recovery blocked, maximum reached"; refunds/
chargebacks and recovery actions beyond `RETRY_SAME_CHECKOUT` are
explicitly deferred (permitted by the master contract's own scope). We
prioritized finishing the financial-safety path completely — proposal
through recovery through audit — over building more breadth partially.
That was a deliberate tradeoff, not an oversight.
