# Demo Script

Operational instructions for running the RazorGrowth AI demo reproducibly.
Every step below was actually driven through the running application in
this repository's own verification pass — nothing here is aspirational.

## Prerequisites

- Node.js 20+, pnpm.
- No Razorpay or Anthropic credentials are required for the demo below —
  the golden path runs entirely on the deterministic rule-based AI
  provider and reaches a clearly labeled "Razorpay Test Mode is not
  configured" state at the payment step (see "Payment step honesty"
  below). If real Razorpay Test Mode keys and/or an `AI_PROVIDER_API_KEY`
  are set in `.env`, the exact same UI flow exercises the live integration
  instead — nothing in the code path changes.

## Reset & start

```bash
pnpm install
pnpm db:up          # starts the local Postgres-compatible dev database
pnpm db:migrate     # apply migrations (idempotent on an already-migrated db)
pnpm db:seed        # DEMO/DEV ONLY — resets and reseeds the one demo merchant
pnpm dev            # starts both apps: API on :4000, web on :5173
```

`pnpm db:seed` is explicitly demo/development tooling: it deletes and
recreates one named demo merchant ("Meridian Athletics") and its data. It
does not touch any other merchant and is not destructive of anything
outside that one seeded record — safe to re-run before every demo run to
guarantee a clean, reproducible starting state.

If `pnpm dev`'s single compound launch ever misbehaves in your terminal
environment, `pnpm dev:api` and `pnpm dev:web` start the two servers
independently on their fixed ports (4000 / 5173) — this is what
`.claude/launch.json` in this repository now uses, precisely to avoid a
port-collision issue documented in `PROGRESS.md`'s Known Issues.

## The canonical demo query

> **"Find black running shoes in size 9 under ₹5,000"**

This exact query is offered as a one-click suggestion on the AI Buyer
page. It deterministically returns a `NEAR_MATCH` result against this
repository's seeded catalog (no exact match under ₹5,000 in size UK9
black exists) — which is the intended demo behavior, not a bug: it
proves the Buyer Agent tells the truth about what it can't find, rather
than fabricating a match.

## 5-minute compressed flow

1. **Overview** (`/overview`) — point at the Agentic Readiness card:
   "Nearly Ready, 78/100, weakest dimension: Payment Reliability." This is
   computed from real catalog/order/payment evidence, not generated by an
   LLM.
2. **AI Buyer** (`/ai-buyer`) — submit the canonical query above. Show the
   interpreted structured intent, the honest "no exact match" framing,
   and the two near-match alternatives with their exact budget-gap
   amounts.
3. **Merchant Agent recovery offer** — click "Ask the Merchant Agent for a
   recovery offer" under a near-match result. It proposes a bounded
   discount sized to close exactly the disclosed gap — then click
   "Evaluate policy": for a >8% gap-closing discount request, the
   deterministic Policy Engine **DENIES** it, even though the Merchant
   Agent proposed it. This is the single strongest "the AI never approves
   itself" moment in the demo — narrate it explicitly.
4. **Growth** (`/growth`) — select "Meridian Pulse Runner," click "Propose
   Growth Action." A real `CROSS_SELL` proposal appears (current basket
   → potential basket → OPPORTUNITY, never "revenue"). Click "Evaluate
   policy": the order total exceeds the auto-approval threshold, so it
   lands `REQUIRE_APPROVAL`. Approve it — watch it become `AUTHORIZED`
   with a real expiry timestamp.
5. **Execute the checkout** — click "Execute authorized checkout." A real
   Order Summary appears with server-computed subtotal/discount/total, an
   order fingerprint, and "Payment status: NOT STARTED."
6. **Payment step honesty** — click "Pay securely — TEST MODE." Without
   configured Razorpay credentials, the server correctly returns "Razorpay
   Test Mode is not configured on this server" — no crash, retry button
   still enabled. Say so plainly: *"With real Test Mode credentials this
   opens Razorpay's actual Checkout widget; the entire payment,
   webhook, and recovery pipeline behind it is proven end-to-end by the
   automated test suite instead — see `docs/EVALUATIONS.md` and
   `PROGRESS.md` for exactly what was and wasn't exercised live."*
7. **Trust Trace** (`/trust-trace`) — pick the workflow chip for the
   growth proposal just created (or paste its workflow ID). Show the
   governance-chain pipeline end to end, click the "Policy Decision"
   node to open its detail drawer (real ledger event, real reason), and
   point at the "Financial outcome" and "Ledger integrity: VERIFIED"
   badges. This is the single screen that makes the whole safety model
   legible without reading a line of source code.
8. **Break the Agent** (`/break-the-agent`) — the memorable "want to try
   to break it?" moment. Click **"Give me a 50% discount."** Watch the
   real result: `AI Proposal → Validation: REJECTED ("Proposed discount
   5000bps exceeds the configured ceiling of 1000bps") → Policy: Not
   Reached → Money moved: ₹0.00`. This is not a scripted animation — it
   is the exact same `validateGrowthProposal` function every real
   proposal in this application passes through.
9. **Close on the principle**: *"The LLM never moves money directly. It
   produces a proposal, which passes validation, deterministic policy,
   approval, and authorization — only then does deterministic code touch
   Razorpay. And when it tries to cheat, the same code that governs the
   real golden path stops it — you just watched it happen."*

## Technical deep-dive (if asked)

- `packages/domain/src/payment-state.ts` — the payment state transition
  table; show `canTransitionPaymentState` rejecting an illegal regression.
- `packages/domain/src/policy-engine.ts` — the four-tier deterministic
  policy evaluation, zero AI/database dependency.
- `apps/api/src/modules/policy/fingerprint.ts` — the proposal fingerprint
  that binds an approval/authorization to an exact, unmutated proposal.
- `apps/api/src/modules/payments/webhook-routes.ts` — the raw-body
  capture + signature verification, before any JSON parsing.
- `packages/domain/src/recovery.ts` — `evaluateRecoveryEligibility`, the
  deterministic gate a payment-failure recovery must pass.
- `GET /api/v1/action-ledger/workflows/:workflowId/verify` and `/trace` —
  the hash-chain verification and the financial-outcome aggregation, both
  built entirely from already-persisted ledger rows.
- `apps/web/src/features/trust-trace/model.ts` — the typed, unit-tested
  transformation from the raw ledger trace into Trust Trace's governance
  stages; a good file to show if asked "is the UI just decoration?"
- `apps/api/src/modules/sandbox/service.ts` — Break the Agent's six
  attacks, each calling a real production function directly.
- `pnpm eval:intent` / `pnpm eval:recommendation` — the two capped AI
  evaluation suites; run them live and read the honest
  "LIVE MODEL EVALUATION NOT EXECUTED" line together.

## What this demo does *not* claim

No real money moves in this environment (visible in the app's own top-bar
banner). No live Razorpay Test Mode transaction was completed in this
build's own verification pass — the full failure→recovery→capture path is
instead proven by 13 real integration tests against a deterministic
provider double that exercises the exact same signature-verification and
state-machine code a live transaction would. See `PROGRESS.md`'s Known
Issues for the precise, non-overclaiming statement of what was and wasn't
exercised live.
