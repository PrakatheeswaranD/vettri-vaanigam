## 1. Executive Summary

Vaanigam answers Track 01's actual question — *"how do you make commerce
safely transactable by AI agents while a human still owns every financial
decision"* — with a working system, not a slide. It is not a chatbot bolted
onto a checkout button. It is a **governance layer**: two narrow, provably
bounded AI agents (a Buyer Agent and a Merchant Agent) that can only ever
*propose*, sitting in front of a deterministic financial core (validation →
policy → approval → authorization → execution → payment → audit) that a
model can never route around.

The codebase already implements the full 00→09 build sequence end to end:
agent-readable catalog & readiness scoring, buyer intent extraction &
grounded recommendation, merchant growth proposals, a four-tier
deterministic policy engine, human approval, execution authorization,
commerce execution, live Razorpay Test Mode payments with signature-verified
webhooks, failure-first recovery, a hash-chained audit ledger, four
agent-commerce protocol adapters (ACP, x402, AP2/SD-JWT, UAP/UCP), full
post-purchase operations (refunds, returns, fulfillment, disputes, GST), an
adaptive per-agent trust score, natural-language policy authoring (diff-only,
never a direct write), a red-team/"Break the Agent" adversarial sandbox, and
a "Trust Trace" governance-chain visualization built from real ledger data.

**What this PRD adds that the existing docs don't:** a single scored
requirements traceability table (Section 6), an honest repo-hygiene audit
that names specific files to remove or consolidate (Section 8), a
severity-ranked fix list (Section 9), and — the highest-leverage section for
"how do we win this" — a tiered set of new, buildable, differentiated
features chosen specifically because they extend load-bearing code that
already exists rather than starting new surface area (Sections 11–12).

## 2. Problem Statement & Why Track 01 Exists

AI shopping agents (ChatGPT Shopping, Perplexity, Gemini, custom LLM
copilots, and soon a wave of protocol-native buyer agents speaking ACP/AP2/
x402/UCP) are starting to transact on behalf of humans. Two things become
true simultaneously the moment that happens:

1. **A merchant's commerce data has to become machine-readable** — price,
   inventory, variant, and policy facts that a language model can ground an
   answer in — or the agent simply cannot transact with that merchant
   reliably, regardless of how good the model is.
2. **Someone has to keep the AI from being the thing that moves money.** An
   agent that can be prompt-injected, that hallucinates a product, or that
   is simply *wrong* about a discount must never be the last line of
   defense before a real charge. A financial system needs a boundary that
   holds even when the model on the other side of it is compromised or
   confused.

Track 01 is scored on **both halves at once**: growth (can an AI actually
buy from this merchant, and can an AI actually grow this merchant) and
safety (does a human — not a probability distribution — retain financial
authority). Most buildathon entries optimize one half. Vaanigam's structural
bet is that the safety half is what makes the growth half durable enough to
trust in production, and the codebase backs that bet with actual
deterministic code, not a disclaimer in a slide.

## 3. Vision & Non-Negotiable Design Principles

> **AI reasons. Deterministic systems retain financial authority.**

Every requirement in this document traces back to one of four sentences
already load-bearing in the code (see `README.md`, `docs/SECURITY.md`):

1. **The LLM never moves money directly.** Every financial action follows
   `LLM → proposal → schema validation → deterministic policy → authorization
   → deterministic execution → Razorpay → verified result → audit event`.
2. **The browser never defines the amount that reaches the payment layer.**
   Every price, discount, and total is rehydrated and recomputed server-side
   at execution time.
3. **The frontend never determines whether a payment succeeded.** Payment
   state comes only from a signature-verified webhook or a direct
   server-side provider fetch.
4. **A financial failure can be understood and recovered without giving the
   AI unrestricted financial authority.** Recovery is one bounded, policy-
   gated proposal type — never a shortcut around the pipeline everything
   else uses.

These four sentences are the product's real moat. Any new feature proposed
in Section 11 is required to preserve all four — that constraint is treated
as a feature-acceptance gate, not a suggestion.

## 5. Scope

**In scope (built):** single-merchant agentic commerce gateway; two AI
agents; deterministic policy/approval/authorization/execution/payment/
recovery pipeline; four protocol adapters at varying maturity; post-purchase
operations; growth/campaign attribution; trust & safety tooling (adaptive
trust score, policy authoring, red-team sandbox, trust trace); multi-currency
domain primitives.

**Explicitly out of scope (stated by the repo itself, not a gap this
document invents):** production multi-tenant identity/KYC/AML; a second
recovery attempt after the first fails; chargeback-initiated refund
automation beyond manual disputes tracking; a distributed cluster-wide rate
limiter; UCP implementation; on-chain x402 settlement; cryptographic SD-JWT
verification for AP2.

## 7. Architecture (Reference)

Modular monolith: one Fastify API, one React/Vite SPA, one Postgres.
`packages/domain` is pure TypeScript with zero framework/SDK dependency and
is the only place financial rules live; `packages/contracts` is the Zod
wire-contract shared by both apps. Three narrow, swappable interfaces carry
all the risk: `CommerceGateway` (read-only), `PaymentGateway` (Razorpay real
+ mock, chosen by environment, never by caller), `AIProvider` (Anthropic /
deterministic rule-based / fixture, chosen the same way). Full detail:
`docs/ARCHITECTURE.md`. This PRD does not restate it; it is correct and
current as inspected.

## 11. Future Roadmap — Tiered, High-Leverage Feature Ideas

Ordered by **effort-to-impact ratio for a jury demo**, not by ambition.
Every idea below explicitly preserves the four non-negotiable principles in
Section 3 — each entry states how.

### Tier A — Finish-what-exists (1–3 days each, highest ROI)

**A1. Real x402 testnet settlement.** Wire a Base Sepolia facilitator
(public or self-hosted reference verify/settle service) behind the existing
x402 challenge/response. *Preserves the boundary because*: settlement is
still gated by the same fails-closed logic already in `modules/x402/
facilitator.ts` — you are replacing a shim behind an existing interface,
not adding a new money-movement path.

**A2. SD-JWT cryptographic verification for AP2.** The parser utility
already exists (`sd-jwt.ts`); add real signature + disclosure verification
against a demo issuer key. Turns "accepted on shape" into "accepted on
cryptography" — closes F3 in the same motion.

**A3. One real, recorded Razorpay Test Mode card-form completion (F1).**
Zero new code. Ten minutes with real test keys. Removes the only open item
in the entire engineering audit.

### Tier B — Proactive Growth (differentiates from every "reactive proposal"
demo, 3–7 days each)

**B1. Autonomous Growth Digest.** Today, the Merchant Agent only proposes
when a merchant selects a product and clicks "Propose Growth Action." Add a
scheduled job that runs the existing, unmodified `OpportunityEngine` across
the *whole* catalog nightly, and surfaces a ranked, capped digest ("3 bounded
opportunities found while you were away") the merchant reviews each morning
— every single proposal in it still goes through the exact same validation →
policy → approval pipeline; only the *trigger* becomes a schedule instead of
a click. This is the single highest-leverage idea in this document: it
turns "AI Growth" from a feature you have to click into a habit a merchant
returns for, without touching the financial safety boundary at all.

**B2. Agent Traffic Analytics.** A dashboard panel splitting traffic and
conversion by *actor class* (Human / AI Buyer Agent / Third-party protocol
agent — the actor classification already exists in Trust Trace's data
model) so a merchant can see "agentic commerce is now 12% of my orders and
converts at 1.4x human traffic" — a concrete, provable growth story a jury
can screenshot.

**B3. Cross-Merchant Agent Reputation Passport.** The Adaptive Agent Trust
Score today is scoped per-merchant (by design — a fresh agent shouldn't
inherit trust it hasn't earned *with this merchant*, and that's the right
call to keep). Extend it with an **opt-in, portable reputation signal**: a
merchant can see "this agent has a clean 90-day history across N other
Vaanigam merchants" as one *additional*, clearly-labeled input alongside
(never replacing) its own local score. *Preserves the boundary because*: it
is read-only evidence surfaced to the same deterministic policy inputs —
the policy engine's decision logic doesn't change, only one more grounded
fact becomes available to it, exactly like the existing `adaptiveTrust`
context parameter pattern.

### Tier C — Jury-Visible Moonshots (higher effort, highest "wow", 1–2 weeks)

**C1. "Prove It" Compliance Export.** One button that generates a signed
PDF/JSON compliance packet for a date range: every policy decision, every
approval, every ledger hash-chain verification result, formatted for a risk
or audit team. This directly extends the existing `/verify` endpoint and
Trust Trace data model — no new financial logic, just a new read-only report
format. Strategically, this is the feature most directly aligned with what
a **payments company's** internship reviewers actually care about: not "can
it demo," but "could a compliance team at a real merchant use this
tomorrow."

**C2. Simulation-as-a-Service (extends Break the Agent).** Let a merchant
paste in *their own* draft policy configuration and run the same six
red-team attacks (plus a synthetic load of typical buyer intents) against
it *before* activating it — "stress-test your policy before you ship it,"
using 100% existing attack code, just re-scoped to a draft config instead of
the live one.

**C3. Multi-modal Buyer Agent input (voice / WhatsApp / image).** The
Buyer Agent's `AIProvider.extractIntent` interface is already
provider-agnostic; add an input adapter that transcribes voice or parses a
WhatsApp Business webhook into the same structured intent schema the text
path already validates. High demo impact, genuinely zero change to the
financial safety boundary — it's a new *front door* onto an unchanged
pipeline.

**C4. Agent-Studio Certification Path.** The repo's own README already
notes Vaanigam is "Agent-Studio-*shaped*" but explicitly not registered with
Razorpay's actual Agent Studio. Turning that into a real, documented
certification checklist — "here is exactly what would need to change to
register this specialist capability with Agent Studio" — is a low-code,
high-narrative move: it shows you understand Razorpay's actual product
strategy, not just the buildathon brief. This is the single idea most
directly aimed at "the reviewers work at Razorpay."

## 12. What Not to Build

Named explicitly, because restraint is part of this product's own stated
philosophy (Jury Q&A: "why not a multi-agent swarm?"):

- **Do not add more AI agents.** A Recovery Agent, Risk Agent, or Pricing
  Agent would each still have to hand off to the same deterministic
  pipeline — pure orchestration overhead with no safety or growth benefit.
  The two-agent design is a stated, defensible choice, not a limitation.
- **Do not let natural-language policy authoring write directly.** It
  returns a diff today; keep it that way even under pressure to "make the
  demo smoother" by auto-applying it.
- **Do not implement a "trust the browser" fast path for any amount,
  discount, or payment state**, no matter how small, even for a demo
  shortcut — this is the one line in the whole architecture that must never
  be crossed, including under deadline pressure.

## 13. Presentation & Submission Strategy

Practical, non-technical advice for the internship outcome specifically:

1. **Lead the demo with Trust Trace or Break the Agent, not the shopping
   flow.** Every buildathon has shopping-bot demos; almost none have a live,
   unscripted "try to break my payment logic" moment. That's the 30 seconds
   that gets remembered.
2. **Say the honest limitations out loud, unprompted** (R3, x402 shim,
   AP2 shape-only). This repo already does this in its own docs — it reads
   as engineering maturity, not weakness, especially to reviewers who will
   ask "is this real" anyway. Volunteering it first is stronger than being
   asked.
3. **Quote real numbers, never rounded ones**: "76 test files, 382 domain
   tests, 41 features complete, 0 unresolved defects" is more credible than
   "extensively tested."
4. **Close on the four principles in Section 3, verbatim.** They're already
   well-written; don't paraphrase them live.
5. **If you implement anything from Section 11 before submission, implement
   A3 first (10 minutes, closes the only open audit item), then B1** (the
   single highest-leverage new feature) **before any Tier C moonshot.**

## Appendix A — Protocol Glossary

- **ACP** (Agentic Commerce Protocol) — OpenAI-originated spec for
  stateful checkout sessions between a buyer agent and a merchant, with
  signed requests and delegated payment tokens.
- **x402** — HTTP 402 "Payment Required" reactivated as a machine-payable
  challenge/response flow, typically settled on-chain (stablecoins on
  L2s such as Base).
- **AP2** — Google-originated "Agent Payments Protocol," cart-mandate
  envelopes carrying **SD-JWT** (Selective Disclosure JWT) verifiable
  credentials.
- **UAP / UCP** — Universal Agent Protocol / Universal Checkout Protocol —
  emerging basket-intake standardization efforts.
- **MCP** — Model Context Protocol — the tool-manifest format agents use to
  discover callable capabilities.
